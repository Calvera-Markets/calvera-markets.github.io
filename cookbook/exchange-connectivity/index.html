Exchange Connectivity

WebSockets lie

WebSockets can be incomplete or inconsistent:

  • Dropped messages — network hiccups, silent disconnects, backpressure
  • Gaps during reconnect — 500ms drop during volatility = missed fills
  • Exchange-side bugs — documented incidents where feeds stopped updating but stayed connected
  • Sequence gaps — if you don’t validate sequence numbers, you won’t know you missed something
  • Buffering under load — during high volatility, exchange infra gets hammered. Messages can be delayed, reordered, or dropped at the broker/CDN layer

REST reconciliation

Periodic REST snapshot every 30-120 seconds. Compare against WebSocket-maintained state. If drift exceeds threshold → trust REST, rebuild state, alert.

WebSocket = speed
REST = truth
Database = source of internal state
Risk engine = final gate

What gets reconciled:

  • Open orders
  • Position sizes
  • Margin balances
  • Funding payments
  • Trade fills

Reconcile on every reconnect. Hard reset on sequence gaps.

“A bot without reconciliation is a bot explaining to risk why it lost 7 figures on phantom inventory.”

Dual-publish pattern

Exchange connectors publish each message to two destinations:

  1. Dedicated mpsc → hot path (TradingCore). Reliable, point-to-point, backpressure-aware.
  2. EventBus (broadcast) → cold-path observers. Best-effort fan-out.

Same data, different delivery guarantees for different consumers.

Stream validation

Every incoming stream must be adversarially validated:

  • Validate sequence numbers
  • Detect gaps
  • Measure message inter-arrival time
  • Monitor heartbeat jitter
  • Track reorder rate

“If you don’t validate the stream, you’re not trading — you’re hoping.”

Exchange personality

“Every exchange has a personality. Learn it.”

  • Undocumented rate limits that appear under load
  • IOC orders behave differently at auction open
  • WebSocket sequence resets at UTC midnight
  • Read the incident history, not just the docs

Order rejection reasons are signal. If reject rates spike, something changed.

Triple-redundancy the feed stack

Beyond periodic REST snapshots, run multiple independent feeds (direct multicast if available, WebSocket + fallback REST + third-party aggregator). Cross-validate in real-time: if any two desync beyond threshold, halt trading.

Crypto exchanges love ghosting feeds during pumps/dumps — assume yours is lying until proven innocent.

Design for exchange failure

Exchanges will:

  • Halt trading
  • Return stale books
  • Misreport balances
  • Liquidate incorrectly
  • Drop private fills

Your system must survive an exchange going insane. Isolate per-venue state. Never let one venue’s failure cascade.

The challenger fund progression

  1. Stage 1: Public APIs — WebSocket order entry, no relationship needed. Every serious crypto fund started here. ~5-50ms latency.
  2. Stage 2: VIP / Market Maker programs — reduced/zero fees, higher rate limits, dedicated connections. Consistent daily volume in the millions gets conversations started.
  3. Stage 3: Institutional onboarding — FIX connectivity, co-location, custom rate limits. You get here by showing up in their volume data, not by cold emailing.
  4. Stage 4: Co-location — Deribit (LD4), CME for crypto futures. Apply, pay, get a rack.

“The moat in crypto isn’t access. It’s strategy quality, execution infrastructure, and risk management.”
