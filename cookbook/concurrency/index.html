Concurrency

Actor model: when to use, when not to

Use actors / async tasks for:

  • Multi-venue orchestration
  • Exchange adapters
  • Risk supervision
  • Reconciliation
  • Reporting
  • Control planes

Don’t use actors for the hot path:

  • Mailbox queuing adds non-deterministic latency
  • Scheduler decisions introduce jitter
  • Message serialization overhead adds cycles
  • Backpressure surfaces as mailbox overflow, not explicit control

“Most people adopt actor models because they’re scared of locks. That’s the wrong reason. Learn to reason about concurrency correctly first — then choose actors because the fault isolation model fits your topology, not because you’re avoiding the hard problem.”

The synthesis

Actor model for the slow path, dedicated channels with owned state for the hot path.

[Hot Path]
Feed Handler → SPSC → Signal Engine → SPSC → Order Router

[Slow Path — actor model fine here]
Risk Monitor
Position Tracker
Reconciliation
Reporting

Channel selection

Channel typeSemanticsUse case
mpsc (bounded)Single consumer, backpressureHot-path market data, signal delivery
broadcastMulti-consumer fan-outCold-path event bus for observers
watchLatest value, single producerLock-free snapshot for API
oneshotSingle value, single useShutdown signals
SPSC ring bufferLock-free, pre-allocatedUltra-low-latency (sub-microsecond regimes)

Rule: Use try_send (non-blocking) on the hot path. Use recv().await only where the await is the entire purpose of the loop iteration (e.g., waiting for the next market event).

Backpressure philosophy

When a consumer is slow:

  • Drop — acceptable for metrics, logging
  • Overwrite — acceptable for snapshot channels (watch)
  • Bounded channel full — try_send fails, caller decides (revert state, alert)
  • Block — never on the hot path

Blocking = death. The hot path must always make forward progress.

The LMAX Disruptor pattern

The canonical solution for hot-path fan-out. A pre-allocated ring buffer with a cursor. Multiple consumers read the same sequence independently without coordinating.

Producer writes to slot N
    ↓
Risk consumer reads slot N    (independent)
Logger consumer reads slot N  (independent)
Metrics consumer reads slot N (independent)

Key properties:

  • Single writer principle — only the hot path writes
  • Pre-allocated — slots exist at startup
  • Cache-line padded — false sharing eliminated
  • Consumers read independently — no coordination between them
  • Publish is a single atomic store to the sequence number
// producer
slot[seq % size] = event;          // write data
release_store(&cursor, seq);       // publish — this is the fence

// consumer
uint64_t available = acquire_load(&cursor);  // this is the fence
if (available >= my_seq) process(slot[my_seq % size]);

No mutex. No condition variable. One atomic operation is your entire synchronization cost.

The fan-out topology

[Hot Path Core 0]
FeedHandler → SPSC → SignalEngine → SPSC → OrderRouter
                                               ↓
                                    [Multicast ring buffer]
                                    /         |          \
                              Risk          Logger      Metrics
                           (Core 2)       (Core 3)     (Core 4)

Risk gets its own read cursor. If risk wants to act (reject an order), it writes to an atomic flag. The hot path checks the flag — one instruction.

Determinism over abstraction

“Actor model is great for correctness. HFT is about mechanical sympathy. Actors optimize developer cognition. HFT optimizes silicon behavior. Different axis.”

In HFT, you want: Input A → Always Output B. Actors can introduce subtle non-determinism (message ordering, race timing, backpressure behavior) that makes replay harder. Replayability is sacred.
