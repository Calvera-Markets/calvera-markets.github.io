Hot Path

The hot path is the critical latency path from market data arrival to order submission. Everything on it must be deterministic, allocation-free, and lock-free.

What belongs on the hot path

On the hot path:

  • Feed ingestion and normalization
  • Order book updates
  • Signal evaluation (synchronous, no I/O)
  • Order construction (price, size, side)
  • The “send” (if transport allows — see Execution Transport)

Off the hot path (cold path):

  • Logging and metrics export
  • Database writes
  • REST API responses
  • Complex risk calculations
  • Portfolio PnL computation
  • Reconciliation
  • ML inference (unless sub-microsecond)
  • Retries and error recovery

The test: if it can block, allocate, or take variable time, it doesn’t touch the hot path.

Information leakage without blocking

The hot path must inform the rest of the system without being slowed down by it.

Principle: The hot path is a write-only, fire-and-forget producer. Everything else is a consumer that earns the right to react — but never gets to slow it down.

Pattern: SPSC ring buffer

Hot Path (producer, pinned core)
    → writes to ring buffer
    → DONE, continues immediately

Slow consumers (separate cores/threads)
    → drain the ring buffer at their own pace
    → risk monitor, logger, metrics, UI

The ring buffer is the seam. The hot path doesn’t know or care what’s downstream.

Key properties:

  • Single writer principle — only the hot path writes
  • Pre-allocated — no GC pressure, slots exist at startup
  • Cache-line padded — no false sharing between producer/consumer cursors
  • If consumers lag, that’s their problem, not the producer’s

When the ring buffer fills: overwrite oldest (lossy). Acceptable for logging and metrics. Never block the producer — if you find yourself blocking, your consumer is too slow or your buffer is too small.

Pattern: Atomic flags for control

The hot path doesn’t call into risk. Risk writes to a flag, hot path reads it:

// Risk thread (slow path)
if position > limit → set halt_flag

// Hot path — one atomic load
if halt_flag → stop sending orders

One atomic load on the hot path. The entire risk system’s complexity is invisible to it.

Pattern: Watch channel for snapshots

Instead of shared state with locks, periodically publish a snapshot via a single-producer channel. Consumers read the latest value without contention.

Hot path: watch::send(snapshot) every N events
API:      watch.borrow() — lock-free, latest value

The hot path is a library, not a binary

Business logic lives in library crates. The binary is pure wiring — it creates channels, spawns tasks, and waits for shutdown. This gives you:

  • Testability without spinning up the full runtime
  • Reuse between live trading and backtesting
  • Clean separation of concerns

Single-threaded deterministic core

The hot path should be single-threaded with exclusive ownership of its state. No Arc, no RwLock, no shared mutable state.

pub struct TradingCore {
    books: BookAggregator,       // owned, no Arc
    funding: FundingAggregator,  // owned, no lock
    strategy: Engine,            // owned, &mut access
}

evaluate() is synchronous — takes borrowed references, returns signals. No async, no I/O.

This makes the hot path:

  • Deterministic — same input → same output
  • Replayable — feed it historical events, get the same signals
  • Cache-friendly — all state is local, no pointer chasing across threads

The deep truth

“The hot path doesn’t leak information. It produces immutable facts. Other parts of the system consume facts. The core doesn’t care if they succeed.”
