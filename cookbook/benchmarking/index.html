Benchmarking & Latency

“Performance benching is about instrumenting system edges, not internals.”

Measure at boundaries, not everywhere

Instrument system edges, not internals:

  • WebSocket message receive
  • Strategy decision timestamp
  • Order send
  • Exchange ACK
  • Fill event

This gives you:

wire → decision latency
decision → send latency
send → ack latency
ack → fill latency

You don’t need logs inside strategy math. You measure transitions.

Monotonic clocks only

Never use wall-clock time for latency measurement. Wall clock jumps. Monotonic doesn’t.

// YES
Instant::now()

// NO
SystemTime::now()

Histograms, not averages

Averages lie. Track:

  • p50
  • p95
  • p99
  • p99.9
  • max

Use HDR Histogram (Gil Tene) for full distribution with minimal memory and zero dynamic allocation. Tail latency kills.

Correlation IDs

Every event carries order_id, client_order_id, trace_id, strategy_id. Reconstruct full lifecycle without extra logging:

market tick → strategy → order → ack → fill → hedge

Never instrument synchronously on the hot path

hot path → write timestamp pair to lock-free ring buffer
                                    ↓
                    background thread drains → metrics store

If measurement adds >1-2 cycles to the hot path, it doesn’t go in.

For the absolute purest hot paths: RDTSC for cycle-accurate, zero-overhead timestamps. Store in a ring buffer, analyze offline.

The latency budget

Think in budgets:

Total tick → order send budget: 15us
Strategy math:  3us
Book update:    4us
Risk check:     2us
Emission:       1us
Slack:          5us

If your “leak” costs 4us, you just killed queue priority. Everything is budgeted.

Monitor jitter, not just speed

Latency isn’t just low vs high. It’s stable vs spiky. Track:

  • Standard deviation
  • Max spike duration
  • Consecutive slow events

Spikes cause queue loss.

Benchmark in isolation AND in production

Synthetic: Replay market data, disable network, measure pure compute.

Live: Measure real RTT, exchange jitter, real contention.

Both matter. A deploy that adds 5us to your hot path is a bug. Regression test on latency, not just correctness.

Separate latency domains

Measure separately:

  • Network latency
  • Strategy compute latency
  • Serialization latency
  • DB latency
  • Lock contention latency

Otherwise you chase ghosts.

Sampling high-frequency paths

At 100k msgs/sec, don’t log everything. Use:

  • Sampling (1%)
  • Aggregated counters
  • Ring buffer stats

Instrumentation itself can become the bottleneck. Never measure in a way that distorts reality.

Hardware-level tools (when serious)

  • perf — CPU sampling, no code changes
  • eBPF/bpftrace — zero-intrusion kernel probes
  • Flame graphs — visual CPU time breakdown
  • Cache miss profiling — sometimes the problem isn’t logic, it’s cache line bouncing
  • NIC hardware timestamps — true wire-level latency, no software clock overhead

The metric that matters

“If you can’t draw a full timeline of one order lifecycle with microsecond precision, you’re not ready.”

The only latency that matters:

tick arrival → order in matching engine

Everything else is intermediate.
