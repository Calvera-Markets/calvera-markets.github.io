Execution Stubbing

The principle

The same hot path code runs in all modes: live trading, paper trading, backtesting, latency profiling. Mode is selected once at startup, never checked per-tick in the hot loop.

Zero divergence between sim and live. If your code behaves differently in sim vs. prod, you’re introducing bugs that only bite when real money is at risk.

Gateway abstraction

Define a trait-based gateway that’s swappable at startup:

trait ExecutionGateway {
    fn send_order(&self, order: &NewOrder) -> Result<OrderAccepted>;
    fn cancel_order(&self, id: &OrderId) -> Result<()>;
}

Implementations:

  • LiveGateway — real exchange connection (REST, WebSocket, FIX)
  • SimulatedGateway — immediate fill with slippage model, maintains fake book
  • NullGateway — drops orders silently, for pure latency profiling
  • ReplayGateway — fills from historical data based on sim rules

Mode selected via config/CLI:

--mode=live       → LiveGateway
--mode=paper      → SimulatedGateway with real market data feed
--mode=backtest   → ReplayGateway
--mode=benchmark  → NullGateway + perf counters

Microstructure-aware stubs

Dumb stubs (immediate fill if crossed) are toy-level. Realistic stubs model:

  • Queue position / priority — your limit order doesn’t fill just because it’s at the best price
  • Adverse selection — you get filled when it’s bad for you
  • Partial fills — not every order fills completely
  • Slippage models:
    • Fixed (constant bps)
    • Linear (bps proportional to size)
    • Depth-based (walks the order book)
  • Latency + jitter on both feed and order legs

Why this matters

  • Single codebase — sim results predict reality because the same code runs everywhere
  • No hot-path branches — mode selected once at init, predictable latency in live
  • Fast iteration — flip to stub mode for debugging without redeploying to colo
  • Risk safety — paper mode uses real feeds but stubbed sends, catches logic bugs before live
  • Benchmark purity — null mode isolates strategy compute from infra latency

Strategy and execution: together or separate?

It depends on your transport.

Co-located / kernel-bypass (~100ns send): Strategy and order submission live on the same thread. The send is the last instruction of the hot path — sub-microsecond, no reason to decouple. Splitting them would only add latency.

Feed → Normalize → Update Book → Evaluate → Send (same thread, same core)

REST / WebSocket (~5-500ms send): Order submission is I/O that would block the strategy loop. You must separate them — fire-and-forget the signal to a dedicated executor task so the strategy keeps processing market events.

Feed → Update Book → Evaluate → try_send(signal)     [hot path, continues]
                                       ↓
                                  Executor task        [separate, handles I/O]

The separation isn’t a design preference — it’s forced by the transport latency. When you upgrade to a transport where the send is fast enough, the executor collapses back into the hot path.

In both cases, the gateway is swapped at startup (live, simulated, null) — backtestability comes from pure functions and trait injection, not thread separation.
