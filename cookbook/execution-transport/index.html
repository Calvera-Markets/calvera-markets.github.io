Execution Transport

Where the send lives, and why it depends on your transport.

The three meanings of “execution”

People conflate three distinct concerns:

ConcernOwnerHot path?
Order generation — “should I send, and what?”Strategy / TradingCoreAlways
Order submission — bytes to exchangeDepends on transportSee below
Execution management — fills, amends, cancels, TWAPOMS / execution algoNever

“The hot path pulls the trigger. Everything else — reloading, aiming the next shot, cleaning the weapon — happens somewhere else.”

Transport determines architecture

Whether order submission belongs on the hot path depends entirely on what “send” costs:

TransportLatencyOn hot path?
Kernel-bypass to coloc~100nsYes, it IS the hot path
Syscall send()~1usYes, acceptable
WebSocket~5-50msBorderline — dedicated task is safer
REST/HTTPS~50-500msNo. Fire-and-forget to dedicated I/O task

If your send takes longer than your inter-event interval, it cannot be on the hot path.

Fire-and-forget pattern (REST/WebSocket regime)

Hot path                          Executor task
   │                                    │
   ├─ recv market event                 │
   ├─ update books/funding              │
   ├─ evaluate strategy                 │
   ├─ mark_entered()                    │
   ├─ try_send(signal) ──────────────►  ├─ recv signal
   ├─ recv next event (immediately)     ├─ pre-trade validity check
   │                                    ├─ POST to exchange (~200ms)
   │                                    ├─ on failure: send opp_id back
   │                                    │
   ◄────────────────────────────────── failure_tx
   ├─ try_recv failures                 │
   ├─ mark_unentered() for each         │
   └─ continue                          │

The mpsc adds ~100ns. The REST call adds 200,000,000ns. The channel is what saves you from your bottleneck.

Duplicate prevention with optimistic marking

  1. Hot path calls mark_entered(opportunity) before sending the signal
  2. Strategy won’t emit duplicate signals for the same opportunity
  3. If try_send fails (channel full): immediately mark_unentered()
  4. If executor reports submission failure: send opp_id back via failure channel, hot path drains and reverts

Two revert paths — both ensure the invariant: if an entry didn’t actually happen, the opportunity stays eligible.

Known limitations of FIFO signal delivery

Signal staleness: The signal carries opportunity state frozen at evaluation time. By the time the executor processes it, the book has moved. Mitigation: executor should re-evaluate against current book state before submitting.

Priority blindness: A marginal 5bps opportunity blocks a screaming 40bps opportunity behind it. Mitigation: priority queue or edge-decay checks in the executor.

The protocol stack

REST/HTTPS
  JSON serialize → TLS encrypt → HTTP frame → TCP → kernel → NIC
  ~50-500ms

FIX over TCP (colo)
  pre-serialized bytes → TCP → kernel → NIC
  ~1-10us

Proprietary binary + kernel bypass (colo)
  pre-serialized bytes → userspace NIC driver → wire
  ~100-500ns

Co-located boxes never make REST calls. That would defeat the purpose.

The upgrade path

REST latency          ~200ms     ← actual bottleneck
Exchange gateway      ~10ms      ← second bottleneck
WebSocket feed lag    ~1ms       ← worth caring about
Signal evaluation     ~1us       ← fine
Channel overhead      ~100ns     ← irrelevant

“Optimize for your real bottleneck, not the bottleneck of a system you don’t have yet.”

Progression for a challenger fund:

  1. Public REST/WebSocket APIs — prove edge, build volume
  2. WebSocket order entry — 10-100x improvement. First real upgrade.
  3. VIP / Market Maker programs — reduced fees, higher rate limits
  4. FIX connectivity + co-location — persistent binary protocol, sub-10us
  5. Kernel bypass — DPDK/Solarflare, send moves back onto hot path

REST is acceptable when

  • Your competition is also on REST (most crypto participants still are)
  • Your holding period makes 200ms entry latency irrelevant (funding arb: 8 hours)
  • You’re in Stage 1-2 of the exchange relationship

REST becomes unacceptable when:

  • You’re competing against WebSocket/FIX-connected participants for the same opportunities
  • Your volume justifies better connectivity but you haven’t upgraded

REST vs WebSocket vs FIX is not a quality judgment — it’s a competitive context judgment. The question is never “is REST good?” It’s “is REST fast enough to capture my edge before my competition does?”
